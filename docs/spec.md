# 芯核適配度檢查器｜規格書

Oct 16, 2026 · @yolanda

## 目標與使用情境

輸入一顆芯核，工具在 10 秒內回答三件事：這顆芯核對每位男主的每個搭檔身份有多適配、值不值得留、升級到目前為止有沒有長歪。

- 使用時機：刷完芯核狩獵、要決定「升／留／拆」的當下，在手機上單手點選完成
- 使用者：《戀與深空》玩家，不需要懂傷害公式
- 不做的事：不算實際傷害數字、不連線遊戲帳號、不做整隊配裝最佳化（第一版）

## 芯核系統規則（工具的計算依據）

工具只認金色（SSR）芯核的完整數值；紫、藍芯核只給「過渡用／拆」的簡易判斷。以下數值為 SSR，來源見最後一節。

**槽位與主詞條**

| 槽位 | 俗稱 | 裝在 | 主詞條可能 | 主詞條 +15 參考值 |
| --- | --- | --- | --- | --- |
| α | 錐子／菱形 | 日冕卡 | 固定生命 | 生命 3000 |
| β | 方塊 | 日冕卡 | 攻擊加成、防禦加成、生命加成、誓約回能、誓約增傷、加速回能 | 加速回能 24%、誓約增傷 14% |
| γ | 海膽／刺球 | 月暉卡 | 固定攻擊 | 攻擊 200 |
| δ | 三角 | 月暉卡 | 攻擊加成、防禦加成、生命加成、暴擊、暴傷、虛弱增傷 | 暴擊 11.2%、虛弱增傷 18.2% |

- 芯核星譜（顏色）必須和思念相同才裝得上；星譜只決定「能裝哪張卡」，不影響搭檔適配分數
- 等級上限：藍 R 9 級、紫 SR 12 級、金 SSR 15 級

| --- | --- | --- | --- |

| 暴傷 | 2.2–3.2% | 1.1–1.6% | 11.2% |
| 虛弱增傷 | 1.8–2.6% | 0.9–1.3% | 9.1% |
| 攻擊／防禦／生命加成 | 7–10% | 3.5–5% | 35% |
| 攻擊（固定值） | 40–60 | 20–30 | 210 |

## 芯核輸入欄位

一顆芯核最多填 8 個欄位，全部用點選或數字鍵盤，不需要打字。副詞條同時填「初始數值」和「目前數值」，工具才算得出升級時強化落在哪幾條。

| 欄位 | 輸入方式 | 選項／範圍 | 必填 | 備註 |
| --- | --- | --- | --- | --- |
| 槽位 | 四顆形狀按鈕 | α 錐子、β 方塊、γ 海膽、δ 三角 | 是 | 選了之後主詞條選單自動過濾 |
| 稀有度 | 三個色塊 | 金 SSR、紫 SR、藍 R | 是 | 決定等級上限 15／12／9 |
| 星譜 | 六個色點 | 綠珥、藍弧、紫輝、黃璃、紅漪、粉珀 | 否 | 只用來顯示，不影響分數 |
| 目前等級 | 加減按鈕 | 0 到該稀有度上限 | 是 | 用來推算已經強化幾次 |
| 主詞條 | 下拉選單 | 依槽位顯示可用的主詞條 | β、δ 必填 | α 自動帶生命、γ 自動帶攻擊 |
| 副詞條種類 | 每列一個下拉選單，最多 4 列 | 暴擊、暴傷、虛弱增傷、攻擊／防禦／生命加成、攻擊／防禦／生命 | 是 | 不能和主詞條重複 |
| 副詞條初始數值 | 每列一個數字框 | 依詞條限制範圍 | 否 | 0 級時看到的數值；沒記下來可以留空 |
| 副詞條目前數值 | 每列一個數字框 | 依詞條限制範圍 | 是 | 現在畫面上的數值 |

- 數值超出上一節表格的範圍時，欄位變紅並提示「這個數值不太可能出現，要不要再看一次？」
- 初始數值高於初始上限（例如暴擊 2.4%），工具自動標記「含 0 級補償強化」，不當成輸入錯誤
- 初始數值留空時，工具用目前數值反推最可能的強化次數，結果旁邊註明「推估」
- 另外有一個全域選項「流派」：暴擊流（預設）或虛弱流，會改變評分權重

## 評分規則

每個搭檔得到一個 0–100 的適配分數：主詞條佔 35%、副詞條佔 65%；α、γ 的主詞條固定，只看副詞條。所有權重寫在資料檔裡，之後可以直接改數字校準，不用動程式。

**步驟 1：副詞條換算成「格數」**

每條副詞條的格數＝目前數值 ÷ 該詞條單次強化最大值。初始一條約 2 格，每強化一次約 +1 格。

| 詞條 | 單次強化最大值（1 格） |
| --- | --- |
| 暴擊 | 0.8% |
| 暴傷 | 1.6% |
| 虛弱增傷 | 1.3% |
| 攻擊／防禦／生命加成 | 5% |
| 攻擊 | 30 |
| 防禦 | 15 |
| 生命 | 600 |

**步驟 2：依搭檔型別給權重（暴擊流）**

| 詞條 | 攻擊型 | 防禦型 | 生命型 |
| --- | --- | --- | --- |
| 暴擊 | 1.0 | 1.0 | 1.0 |
| 暴傷 | 1.0 | 1.0 | 1.0 |
| 虛弱增傷 | 0.6 | 0.6 | 0.6 |
| 攻擊加成 | 0.8 | 0.4 | 0.4 |
| 防禦加成 | 0 | 0.8 | 0 |
| 生命加成 | 0 | 0 | 0.8 |
| 攻擊 | 0.4 | 0.2 | 0.2 |
| 防禦 | 0 | 0.4 | 0 |
| 生命 | 0 | 0 | 0.4 |

- 切到虛弱流時：暴擊、暴傷改成 0.3，虛弱增傷改成 1.0（虛弱狀態下暴擊與暴傷不生效）
- 防禦型的攻擊加成只給 0.4，是因為光獵、永恆先知的倍率裡防禦項遠大於攻擊項

**步驟 3：主詞條分數（只算 β、δ）**

| 槽位 | 1.0 分 | 0.8 分 | 0.2 分 |
| --- | --- | --- | --- |
| β | 加速回能、誓約回能、誓約增傷 | 對應型別的加成（攻擊型配攻擊加成，以此類推） | 不對應的加成 |
| δ | 暴擊、暴傷（暴擊流）；虛弱增傷（虛弱流） | 對應型別的加成；虛弱增傷（暴擊流） | 不對應的加成 |

**步驟 4：合併**

```latex
\text{副詞條比}=\frac{\sum(\text{格數}_i\times\text{權重}_i)}{\sum\text{格數}_i}
```

```latex
\text{適配分}=100\times(0.35\times\text{主詞條分}+0.65\times\text{副詞條比})\quad(\alpha,\gamma\ \text{則}=100\times\text{副詞條比})
```

- 紫 SR：分數 × 0.6，並標「過渡用」；藍 R：不算分，直接建議拆
- 權重表是第一版的估值，不是實測傷害；要靠你實際用幾顆芯核比對後再調整

## 長歪判定

「長歪」＝升級時的強化，大部分落在對目標搭檔沒用的副詞條上。工具比對初始和目前數值，算出每條各被強化幾次，再看好詞條吃到幾次。

**計算方式**

1. 已發生的強化次數 n＝目前等級 ÷ 3 取整數（+3、+6、+9、+12、+15 各一次）
2. 每條副詞條的強化次數＝（目前數值 − 初始數值）÷ 該詞條單次強化的中間值，四捨五入；中間值：暴擊 0.675%、暴傷 1.35%、虛弱增傷 1.1%、各種加成 4.25%、攻擊 25、防禦 12.5、生命 500
3. 好詞條＝對「分數最高的那個搭檔」權重 ≥ 0.8 的詞條；好強化次數＝落在好詞條上的次數加總
4. 初始數值留空時，用目前數值扣掉初始中間值來推估，並在結果標「推估」

**判定標籤**

| 標籤 | 條件 | 給你的建議 |
| --- | --- | --- |
| 還沒開始長 | n＝0 | 看初始詞條就好，先升到 +3 看第一次強化 |
| 長得很好 | 好強化次數 ≥ n × 2/3 | 值得繼續升 |
| 普通 | 介於兩者之間 | 看適配分決定 |
| 長歪了 | 好強化次數 ≤ n × 1/3 | 停手，考慮拆掉回收芯核能量 |

**後續預估**

- 剩餘強化次數＝（等級上限 − 目前等級）÷ 3 取整數
- 每次強化落在好詞條的機率，先假設＝好詞條數 ÷ 現有副詞條數（強化平均分給現有每一條；這是假設，待確認）
- 顯示一句話，例如：「還能再長 3 次，每次大約 50% 會長在暴擊或暴傷上」
- 天生只有 2 條副詞條、而且兩條都是好詞條的金芯核，標「極品胚子」，因為之後所有強化都會落在這 2 條

## 介面規格

單一頁面、手機直式優先：上半部輸入，按「檢查」後往下捲到結果。整個流程單手操作，主要按鈕都在拇指範圍內。

- 版面：寬 360–430px 為主，桌機置中最大寬 480px；左右留白 16px，不出現橫向捲動
- 色系：粉色可愛風。主色柔粉、輔色奶白與淡紫，結論卡片用圓角大卡片；深色模式改成深莓底＋粉色字
- 字體：思源黑體或系統字，數字用等寬數字方便對齊
- 按鈕：槽位用四個形狀圖示按鈕；稀有度與星譜用色塊；等級用 − / ＋ 按鈕
- 輸入順序：槽位 → 稀有度 → 等級 → 主詞條 → 副詞條四列 → 檢查
- 副詞條每列：左邊詞條下拉、中間初始數值、右邊目前數值；數字框叫出數字鍵盤（`inputmode="decimal"`）
- 結果區：總結論卡片 → 長歪區塊 → 男主篩選按鈕 → 搭檔分數清單
- 「清空重填」固定在底部；「流派」切換放在頂部右上角
- 文案語氣：口語、溫和，不用「顯然」「你應該」這類字眼

## 技術架構與實作清單

純前端、無後端：計算邏輯全部是純函式，資料放在兩個 JSON 檔，最後打包成單一 HTML 發布成 artifact，手機直接開連結使用。

&#91;embedded content: 工具架構 · 5 個計算模組＋2 個資料檔\]

輸入依序經過驗證、評分、長歪判定再顯示；三個計算步驟都從資料層讀數字，不在程式裡寫死任何數值。

**檔案結構**

- `data/rules.json`：第 2 節的主副詞條範圍、第 5 節的格數與權重、第 6 節的強化中間值、第 7 節的門檻
- `data/companions.json`：每筆 `{ id, lead, name, aliases, type, verified, source }`，`type` 只能是 `atk`／`def`／`hp`／`unknown`
- `src/validate.js`、`src/scoring.js`、`src/growth.js`：只吃資料、吐結果的純函式，不碰畫面
- `src/input.js`、`src/result.js`：畫面
- `tests/`：每個純函式至少 3 個測試，包含下方範例芯核
- 打包時把兩個 JSON 內嵌到 `<script type="application/json">`，輸出單一 `index.html`

**給 code 模式的實作順序**

- [ ] 建立 `rules.json`，數字全部照本文件第 2、5、6、7 節
- [ ] 建立 `companions.json`：先放 3 個已核對的；其餘 24 個逐一打開 BWIKI 搭檔頁，依第 3 節判定方法填 `type` 與 `source`
- [ ] 寫 `validate.js`、`scoring.js`、`growth.js` 與測試，先讓下方範例芯核的分數算對
- [ ] 寫畫面，照第 8 節介面規格
- [ ] 打包成單一 HTML 並發布成 artifact
- [ ] 拿 5 顆自己的真實芯核試算，回頭調整權重

## 待確認事項

以下 8 點會影響分數準確度，前 3 點最優先；第一版可以先照目前假設做，標「推估」讓使用者知道。

- [ ] 其餘 24 個搭檔的型別（攻擊／防禦／生命），照第 3 節方法查 BWIKI
- [ ] 有沒有「只吃攻擊」的純攻擊型搭檔；目前查到的 3 個都是攻擊加另一種屬性
- [ ] 強化是否平均隨機分給現有每一條副詞條（第 6 節的機率預估靠這個假設）
- [ ] 天生 3 條副詞條的金芯核，+3 時是新增第 4 條還是強化現有的；不同攻略說法不一，工具用「比對數值」的方式繞開這個問題
- [ ] 誓約增傷會不會出現在副詞條；有攻略把它列為推薦副詞條，但詞條表裡沒有
- [ ] 紫 SR、藍 R 芯核的副詞條數值範圍；目前只查到金色的
- [ ] 台服的搭檔與詞條譯名，填進 `aliases`
- [ ] 第 5 節權重表要用真實芯核校準；神話武器等新機制可能改變最佳詞條
